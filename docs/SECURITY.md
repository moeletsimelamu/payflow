# PayFlow security

PayFlow is a **simulation**: it never accepts card numbers, moves real money or talks to a card
network. It still handles credentials, merchant data and financial records, so it is built and
reviewed as if it were real. This document is the Phase 9 security review against the
**OWASP Application Security Verification Standard 5.0, Level 2**, the findings it produced, and
what is still open.

Design summary: [ARCHITECTURE.md §7](ARCHITECTURE.md#7-security-architecture-summary--detailed-in-securitymd).
How the controls are tested: [TESTING.md](TESTING.md).

## 1. Findings

Severity is judged for a payments platform: anything that lets a user keep or gain privileges, or
weakens authentication of the platform admin, is High.

| ID | Severity | Finding | Status |
|---|---|---|---|
| SEC-1 | **High** | **Security-stamp revalidation was switched off.** `ConfigureApplicationCookie` assigned a new `CookieAuthenticationEvents`, which replaced the handler `AddIdentityCookies` had registered. Roles and merchant memberships live in the session cookie, so a removed member or demoted admin kept their access for as long as they kept the session active, and a password change did not end other sessions. | **Fixed.** `SessionLifetime` runs the security-stamp check again (every minute). `SessionLifetimeTests` fail without the fix and pass with it. |
| SEC-2 | **High** | **No multi-factor authentication for platform admins.** A platform admin can register and close merchants, run settlements and payouts, and resolve reconciliation exceptions; a password was the only factor. ASVS 5.0 Level 2 requires MFA (V6). | **Fixed.** TOTP authenticators (RFC 6238), required for platform admins and optional for merchant users. A password alone gives only a 5-minute pending sign-in; platform admins without an authenticator must set one up before they get a session, and existing admin sessions without a second factor end. Secrets encrypted at rest; each code accepted once (atomic step check); 10 single-use recovery codes stored as salted SHA-256; failed codes count towards the lock-out, and a correct password no longer resets the failure count for MFA users. `TotpTests` (RFC 6238 and 4648 vectors), `MfaTests`, dashboard specs, and the E2E suite signs the admin in with a code. |
| SEC-3 | Medium | **No absolute session lifetime.** Sessions slid by 30 minutes on every request and never forced re-authentication while active. | **Fixed.** Sessions end 12 hours after sign-in, however active (`SessionLifetime`, `SessionLifetimeTests`). |
| SEC-4 | Medium | **Passwords were not checked against breached or common passwords.** The policy is 12+ characters with 4 unique characters (NIST SP 800-63B length over composition), but `password1234` passed. | **Fixed.** Every password set (invitation acceptance, user creation) is checked, ignoring case, against the 46,146 entries of 12+ characters among the million most common breached passwords (SecLists, MIT; bundled, no network call), and refused if it contains the user's email name, display name or "PayFlow". `CommonPasswordValidatorTests`, `PasswordPolicyTests`. |
| SEC-5 | Medium | **Load-induced denial of service.** At 100 payments/s the synchronous console log sink blocked request threads while database transactions were open; with Npgsql's default pool of 100 the API then took every Postgres connection. p95 reached 16 s and 14 % of requests failed with `53300 too many clients`. | **Fixed.** Asynchronous log sink, ledger account cache, pool capped at 32. 100 req/s: p95 73 ms, 0 errors (TESTING.md, "Load test"). |
| SEC-6 | Low | **Trace context would have leaked to merchants.** With OpenTelemetry's HttpClient instrumentation, webhook requests would carry `traceparent`, exposing internal trace ids to third-party servers. | **Fixed before release.** The webhook handler uses a no-output propagator (`WebhookTracePropagationTests`). |
| SEC-7 | Low | **Container secrets are environment variables.** Compose passes database, Redis, pepper and master-key secrets as environment variables, readable with `docker inspect` by anyone with Docker access. ARCHITECTURE.md said "Docker secrets". | **Open (accepted for local use).** ARCHITECTURE.md corrected. A production deployment must inject them from a secret store or as mounted secrets. |
| SEC-8 | Low | The dashboard's Content Security Policy allows `style-src 'unsafe-inline'` (Angular component styles). Scripts are `'self'` only. | **Accepted.** No inline script is possible; style injection alone cannot run code. |
| SEC-9 | Low | The Compose demo turns off the webhook SSRF guard's private-network check (`Webhooks__AllowPrivateNetworks`) and allows HTTP, so the API can reach the bundled `webhook-sink`. | **Accepted for the local demo only.** Both are off by default in code, and the integration tests run with the guard on (`SsrfGuardTests`, `WebhookTests`). Never set them in production. |
| SEC-10 | Low | The optional `otel-dashboard` (Compose profile `observability`) accepts OTLP without authentication. | **Accepted.** Reachable only on the internal Compose network; its UI is bound to 127.0.0.1 and asks for a one-time token. |
| SEC-11 | Info | `npm audit` reports 16 moderate advisories, all in the Angular CLI's own tooling (npm, sigstore, glob, minimatch). | **Accepted.** Development only, never shipped. `npm audit --omit=dev` is clean, and CI fails on any high advisory in production dependencies. |
| SEC-12 | Info | ARCHITECTURE.md described the API-key limit as "100 req/s burst, 6000/min" and a per-username login limit. The real controls are 600 requests a minute per API key, 10 sign-ins a minute per client IP, and account lock-out after 5 failures. | **Fixed.** ARCHITECTURE.md corrected. The lock-out covers what a per-username limit would. |

## 2. Review by ASVS 5.0 chapter

"Evidence" names the code and the tests that prove each control. Chapters that do not apply say why.

| Chapter | Controls in PayFlow | Evidence | Gaps |
|---|---|---|---|
| **V1 Encoding and sanitization** | EF Core and parameterised SQL only (interpolated `ExecuteSqlAsync`/`SqlQuery` are parameterised); Angular's contextual output escaping; no HTML is built on the server. Reconciliation CSV is parsed as data with a strict schema, never evaluated. | `ReportingQueryTests` (`Bad_queries_are_rejected`), `ReconciliationEngineTests` (`Csv_round_trips_and_rejects_every_bad_line_at_once`) | — |
| **V2 Validation and business logic** | FluentValidation on every request; strict JSON (unknown properties rejected); money as `decimal`/`numeric` with per-currency precision; state-transition whitelists; idempotency keys on every financial write; refund reservation and DB check constraints so business rules hold even if code is bypassed; card-number (Luhn) detector on every string field. | `Unknown_json_properties_are_rejected`, `PaymentDomainTests`, `Fifty_concurrent_identical_requests_create_exactly_one_payment`, `Card_numbers_are_refused_in_every_field_and_never_stored`, `DatabaseIntegrityTests`, k6 replay checks | — |
| **V3 Web frontend security** | Single origin behind the gateway; CSP `default-src 'self'; script-src 'self'; frame-ancestors 'none'`; HSTS; `X-Content-Type-Options`; `Referrer-Policy`; `Cross-Origin-Opener-Policy`; `Permissions-Policy`. Session cookie `__Host-`, `HttpOnly`, `Secure`, `SameSite=Strict`; no tokens in browser storage. | `Responses_carry_defensive_headers_and_are_never_cached`, `Admin_logs_in_with_a_hardened_session_cookie`; headers checked through the gateway with curl | SEC-8 (accepted) |
| **V4 API and web service** | Merchant API: bearer API keys, never cookies, so it is CSRF-exempt by construction. Dashboard API: double-submit antiforgery on every state change, HTTPS only. RFC 9457 problem details with a correlation id and no internals. Per-key quota in Redis. | `Login_without_an_xsrf_token_is_rejected`, `Unknown_routes_return_problem_details_with_a_correlation_id`, `Each_key_has_a_request_quota_shared_through_redis` | — |
| **V5 File handling** | No file uploads. Statements are submitted as CSV text, size-limited, hashed for de-duplication and parsed in memory. Settlement CSV is generated server-side. | `ReconciliationTests` (duplicate import refused) | — |
| **V6 Authentication** | ASP.NET Core Identity; PBKDF2-HMAC-SHA512 at 210,000 iterations; 12+ character passwords with no composition rules, refused if breached or built on the user's own details; lock-out after 5 failures for 15 minutes; identical response and timing for unknown user, wrong password and lock-out; 10 sign-ins a minute per IP; one-time invitation tokens (3-day lifetime) delivered in the URL fragment, never a query string. TOTP second factor: required for platform admins, optional for merchant users, codes and recovery codes single-use. API keys: 256-bit secrets, stored as HMAC-SHA256 with a server pepper, compared in constant time, shown once, rotation with a grace period. | `Wrong_password_and_unknown_user_get_identical_responses`, `Five_failures_lock_the_account_even_for_the_correct_password`, `Login_is_rate_limited_per_client`, `Invitation_tokens_work_once_and_the_last_admin_cannot_be_removed`, `ApiKeyTests`, `TotpTests`, `MfaTests`, `CommonPasswordValidatorTests`, `PasswordPolicyTests` | SEC-2, SEC-4 (fixed) |
| **V7 Session management** | Server-side-validated cookie sessions: 30-minute sliding expiry, 12-hour absolute lifetime, security stamp and claims re-checked every minute, logout ends the session and clears the XSRF cookie. | `SessionLifetimeTests`, `Logout_ends_the_session` | SEC-1, SEC-3 (fixed) |
| **V8 Authorization** | Policies `PlatformAdmin`, `MerchantAdmin`, `MerchantMember`; every merchant route checks membership of *that* merchant; another merchant's resources are 404, its routes 403. Operator refunds capped per merchant; platform admins cannot move merchant money. | `MerchantAccessHandlerTests`, `Merchant_users_cannot_see_other_merchants_or_platform_endpoints`, `Another_merchants_key_is_not_found_through_your_own_merchant`, `Operators_refund_within_their_limit_and_platform_admins_cannot_move_merchant_money`, `Reconciliation_is_for_platform_admins_only` | — |
| **V9 Self-contained tokens** | Not used: sessions are opaque cookies, API keys are random secrets looked up server-side. | — | Not applicable |
| **V10 OAuth and OIDC** | Not used. | — | Not applicable |
| **V11 Cryptography** | Webhook signatures: HMAC-SHA256 over timestamp and body, 5-minute replay window, test vectors. Webhook secrets and the cookie key ring encrypted with AES-256-GCM (ASP.NET Data Protection) under a master key from the environment. API keys, webhook secrets and encryption keys and nonces come from `RandomNumberGenerator` (CSPRNG); record ids are UUIDv7 and are not secrets. No custom algorithms. | `Signatures_match_independently_computed_vectors`, `Tampering_with_body_timestamp_or_secret_is_detected`, `Replays_outside_the_tolerance_window_are_rejected`, `Data_protection_keys_are_persisted_in_the_database` | — |
| **V12 Secure communication** | TLS terminated at the gateway (Caddy), HSTS; the API trusts `X-Forwarded-*` only from the gateway's network; ports bound to 127.0.0.1. Tests never turn TLS verification off: k6 and Playwright verify against Caddy's CA. Webhooks: HTTPS only outside the demo. | Compose file; `tests/load`, `tests/e2e` | SEC-9 (demo only) |
| **V13 Configuration** | No secrets in `appsettings.json` or the repository; startup fails if a required secret is missing; dependency vulnerability scans in CI (.NET and npm); pinned package and image versions; non-root dashboard image. | CI workflow; `.env.example` | SEC-7, SEC-11 |
| **V14 Data protection** | No card data ever accepted. Secrets shown once and stored only as HMACs or ciphertext. `Cache-Control: no-store` on API responses. Logs, traces and attempt records redact credentials, cookies, signatures and secrets; traces carry parameterised SQL, never parameter values. | `RedactionTests`, `Serilog_policy_never_logs_a_login_password`, `A_new_key_authenticates_the_merchant_api_and_its_secret_is_never_stored_or_logged`, `WebhookTracePropagationTests` | — |
| **V15 Secure coding and architecture** | Modular monolith with enforced module boundaries; webhook SSRF guard at connect time (resolved address checked, no redirects, no proxy); bounded resources (connection pool, rate limits, log buffer, webhook timeouts and response-size caps); concurrency handled with row locks, `SKIP LOCKED` and advisory locks. | `ArchitectureRules`, `The_handler_refuses_to_connect_to_private_addresses_at_connect_time`, `Unsafe_endpoint_urls_are_refused`, chaos test, k6 | SEC-5 (fixed) |
| **V16 Logging and error handling** | Structured JSON logs with correlation, trace and span ids; append-only audit log for every privileged action and sign-in, enforced by grants and triggers; generic error responses; OpenTelemetry traces and metrics. | `App_role_has_no_update_or_delete_privilege_on_audit`, `Audit_records_cannot_be_changed_even_by_the_schema_owner`, `Successful_login_is_audited_with_the_request_correlation_id`, `TelemetryTests` | — |
| **V17 WebRTC** | Not used. | — | Not applicable |

## 3. Verification performed in Phase 9

- **Automated tests:** 512 backend tests (unit, architecture, integration on real PostgreSQL and Redis via Testcontainers) and 100 dashboard tests including axe accessibility checks. CI enforces coverage minimums.
- **End-to-end:** Playwright runs the 11 reviewer scenarios against the Compose stack. The chaos suite SIGKILLs the API four times under load and checks that nothing is lost or duplicated.
- **Load:** k6, 100 payments/s for 2 minutes through the TLS gateway, 10 % idempotent replays.
- **Manual review:** response headers through the gateway; cookie flags; database grants (`deploy/postgres/sql/roles.sql`); dependency audits (`dotnet list package --vulnerable`, `npm audit`); every configuration switch that weakens a control (SEC-7, SEC-9, SEC-10).

## 4. Reporting a vulnerability

Please report suspected vulnerabilities privately through the repository's GitHub security
advisories ("Report a vulnerability"), not in a public issue.
